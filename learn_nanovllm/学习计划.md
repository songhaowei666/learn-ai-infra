# Nano-vLLM 调度层学习计划

以 nano-vLLM 为教材、按仓库根目录 `AGENTS.md` 边界执行。  
核心代码很少：调度相关约 **400 行**（`scheduler` + `block_manager` + `sequence` + `llm_engine`），适合从头啃透。

---

## 总原则

| 做 | 不做 |
|----|------|
| 读懂「请求怎么排队 → 组 batch → 占/放 KV → 抢占/结束」 | 不啃 `layers/`、Triton、CUDA Graph、TP 实现 |
| 每阶段产出一张图或一段笔记 | 不为跑分、不为写算子 |
| 浅学点只记名词直觉 | 不滑向训练/炼丹 |

**建议节奏**：每周 3–5 小时，约 **4 周** 完成主线；主业忙就拉长，但不要跳过阶段验收。

---

## 第 0 周：地图与名词（0.5–1 天）

**读**：`目录作用说明.md` + `nano-vllm/example.py` + `nano-vllm/nanovllm/llm.py`（薄封装）  
**浅学**（不看源码细节）：Prefill / Decode、Continuous batching、PagedAttention、吞吐 vs 延迟

**验收**：能用自己的话画出分层：

```
API → Engine(调度+KV) → ModelRunner → Model/Layers
```

并说出：你只深挖中间那一层。

---

## 第 1 周：一次请求的完整路径（深入起点）

**精读顺序**：

1. `engine/sequence.py`（~83 行）— 序列状态、token/block 计数
2. `engine/llm_engine.py`（~90 行）— `add_request` → `step` → `generate`
3. `engine/scheduler.py` 的 `add` / `schedule` / `postprocess`（先不抠 preempt）

**产出笔记**（放本目录）：

- 一张时序图：prompt 进来 → WAITING → RUNNING → FINISHED
- 列出 `SequenceStatus` 与谁改状态

**验收**：指着 `llm_engine.step()` 讲清一步里调了谁、返回了什么。

---

## 第 2 周：Scheduler 决策（深入 #1）

**精读**：`scheduler.py` 全文（~92 行）

重点搞清：

- waiting vs running 两个队列
- prefill 与 decode 各自如何进 batch
- `max_num_seqs` / `max_num_batched_tokens` 如何卡吞吐
- `preempt`：何时抢、谁被抢、抢完回哪

**产出**：

- 「调度一步决策树」（可手绘）
- 约束清单草稿：什么情况下新请求进不了 batch

**验收**：给定「waiting 里 2 条长 prompt、running 里 3 条 decode、KV 快满」的假场景，能口头推演本轮 schedule 结果。

---

## 第 3 周：BlockManager + Prefix Cache（深入 #2）

**精读**：`block_manager.py`（~120 行）+ `sequence` 里与 `block_table` 相关的字段

重点搞清：

- block 分配 / 释放 / `ref_count`
- `can_allocate` / `allocate` / `can_append` / `may_append`
- hash → 前缀命中 → 少算多少 token
- 抢占或结束后 cache 如何失效

**产出**：

- 「KV 生命周期」图：allocate → append → hash 复用 → deallocate
- 补全约束清单：多轮/前缀复用时上层不能假设什么

**验收**：能解释「两条共享前缀的请求」在 allocate 时发生了什么；抢占后 prefix cache 还在不在。

---

## 第 4 周：串起来 + 上层约束清单（深入 #3/#4）

**串读**：再走一遍 `llm_engine` ↔ `scheduler` ↔ `block_manager`，对照假想多轮会话。

**浅扫即可**（知道调用关系就停）：

- `model_runner.py`：它吃 schedule 结果、跑前向（不追 CUDA Graph / TP）
- `utils/context.py`：prefill 标志、`block_tables` 等如何传给 Attention（只记「调度结果如何被消费」）

**最终产出**（本仓库最有价值的交付物）：

1. **一次请求完整调度路径**（一页图 + 注释）
2. **调度约束清单**（上层设计「不能做什么」）— 例如：不假设 KV 永驻、不假设不会被抢占、前缀复用有条件等

**验收**：换一个上层场景（长会话、突发并发、共享 system prompt），能判断会不会把调度/KV 打崩，并指出卡在哪一行逻辑。

## 刻意不学（遇到就绕开）

| 文件/主题 | 处理方式 |
|-----------|----------|
| `layers/*`、`models/qwen3.py` | 不看实现；知道「算 attention、写 KV」即可 |
| Triton / CUDA Graph / Torch Compile | 标题级：知道是加速手段 |
| `bench.py` 刷分、TP 细节 | 跳过 |
| 训练、SFT、RLHF | 完全排除 |

## 推进方式

若每周可投入时间不同，可压成「两周速通」或拉成「六周慢啃」。
